For the longest time, GitHub was just "that place with the cat logo where I upload my assignments." I knew *of* git. I did not know git. There's a difference, and I found that out the hard way more than once.

## Where I Started

My first "workflow" was genuinely just:

```bash
git add .
git commit -m "fix"
git push
```

Over and over. Every commit message said "fix." Future me had zero idea what any of it fixed. If you've done this too, no judgment — we've all been there.

## The Moment It Clicked

The thing that finally made git make sense wasn't a tutorial, it was breaking my own project badly enough that I had to actually understand what a commit was to undo my mistake. Turns out commits are just checkpoints — snapshots of your project you can go back to. Once I understood that, everything else started falling into place.

```bash
git log --oneline
git checkout <commit-hash>
```

Suddenly git wasn't scary, it was a safety net.

## Branches Finally Made Sense Too

I used to think branches were an "advanced" feature for real developers. Turns out they're just: make a copy of your code, mess around freely, and merge it back in once it works.

```bash
git checkout -b add-new-feature
# do your thing, break stuff, fix it
git checkout main
git merge add-new-feature
```

No more being terrified to experiment directly on `main`.

## What I'd Tell Past Me

- Commit often, and actually write what you changed, not just "fix"
- Branches are for trying things, not just for "serious" projects
- `git status` is your friend — run it constantly, it always tells you what's going on
- Breaking something isn't a disaster, it's just a `git log` away from being fixed

## Wrapping Up

Learning GitHub properly didn't happen through a single course, it happened through a lot of small confused moments and slowly building actual intuition for what these commands were doing. If you're still in the "commit message says fix" phase — you're doing fine. Keep going.
